# Decision Log & Traceability Matrix

This document is the authoritative record of every non-trivial implementation decision made while migrating the original raw Node.js `http` server into a production-ready Express.js application. It is the single source of truth for the "why" behind those decisions (per the Explainability rule); that rationale is intentionally kept here and is **not** duplicated in code comments anywhere in the project.

## Decision Log

| D18 | Harden the `server.js` lifecycle: (1) a server `'error'` listener writes one structured `logger.error` entry with the fixed text `HTTP server error` and the error's `code`, `syscall`, `address`, `port`, and `message` (Winston appends that `message` to the fixed text), then exits with code 1, and `server.listen` runs inside a `try`/`catch` that passes an error thrown synchronously (such as `ERR_SOCKET_BAD_PORT` for `PORT=-1` or `PORT=65536`, which `parseInt` accepts) to the same listener, so it also yields that single entry and exit 1; (2) only the first SIGTERM/SIGINT starts shutdown, and later signals log one `warn` line each and never call `server.close` again; (3) an error passed to the `server.close` callback is logged at error level with its `code` and message and exits 1, otherwise `HTTP server closed` is logged and the process exits 0 as before; (4) shutdown starts a hardcoded `SHUTDOWN_TIMEOUT_MS = 4000` timer, `unref()`'d, that logs an error-level `Graceful shutdown timed out after 4000 ms: forcing exit` entry and exits 1 if connections have not drained; (5) every terminal outcome of (1), (3) and (4) goes through one `terminate` function: the first outcome wins and later ones are ignored, it marks shutdown as started (so later signals take the `warn` path of (2)) and clears the 4000 ms timer, writes the outcome's log entry, waits one event-loop turn (`setImmediate`), then waits until every pending `process.stdout`/`process.stderr` write has completed, bounded by a hardcoded `LOG_FLUSH_TIMEOUT_MS = 500`, and only then calls `process.exit` with the outcome's code. (g) was rejected because PM2 formats an empty write as a `<log_date_format>: ` fragment, leaving a dangling partial line in the merged `./logs/` files; (h) because Winston emits `finish` once the Console transport has acknowledged the entry, before the stream write completes, and later log calls (a repeated-signal `warn`, Morgan lines of in-flight requests) would hit write-after-end; (i) because the PM2 cluster IPC channel and open sockets keep the event loop alive; (j) because a fixed delay neither guarantees completion nor ends as soon as the output is written; (k) because the refinement adds no transports. 500 ms keeps the worst-case forced exit at 4000 + 500 = 4500 ms, below PM2 `kill_timeout: 5000` | Requests running longer than 4 s are cut off during shutdown; a forced or failed shutdown returns exit code 1, which callers see as a failure even though the stop was requested. The timeouts are code constants, so changing them requires a code change. Output still pending 500 ms after a terminal outcome is abandoned, and every exit waits up to 500 ms for its output, so the 4 s forced exit completes within 4.5 s. Every `stdout`/`stderr` write for the life of the process passes through the counting wrapper (one counter update and one closure per write). Only the first terminal outcome is acted on: a later one (for example a close callback that arrives during the timeout's 500 ms flush window) is neither logged nor allowed to change the exit code |
