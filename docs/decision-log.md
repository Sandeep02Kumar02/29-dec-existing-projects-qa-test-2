# Decision Log & Traceability Matrix

This document is the authoritative record of every non-trivial implementation decision made while migrating the original raw Node.js `http` server into a production-ready Express.js application. It is the single source of truth for the "why" behind those decisions (per the Explainability rule); that rationale is intentionally kept here and is **not** duplicated in code comments anywhere in the project.

## Decision Log

| ID | Decision | Alternatives Considered | Rationale | Risks / Mitigation |
|----|----------|-------------------------|-----------|--------------------|
| D1 | Adopt Express `5.2.1` | Express 4.x; Fastify; Koa; remain on core `http` | Prompt explicitly names Express; v5 is current stable with built-in body parsing and modern routing; requires Node `>=18` (Node 22 satisfies) | v5 has breaking changes vs v4; low risk on a greenfield app. `npm audit --omit=dev` reports the transitive `qs` `6.15.3` (pulled in by `express` `5.2.1` and `body-parser` `2.3.0`) as moderate: GHSA-x5fp-wj9c-mxmx (array-limit bypass via bracket-key comma parsing) and GHSA-4mjr-xmp4-gh2g (DoS via an attacker-controlled `isBuffer`). Exposure is limited because Express 5's default `simple` query parser uses Node's `querystring`, so `qs` is reached only by `express.urlencoded`, which parses flat (`depth: 0`, D21). Accepted risk: the `express` `5.2.1` pin is retained per AAP §0.6.1 and the minimal-changes rule |
| D2 | Winston `3.19.0` for structured logging | Pino; bunyan; `console` only | Mature transports/levels/formats, widely documented | Heavier than Pino; acceptable at this scale |
| D3 | Morgan `1.11.0` for HTTP logs piped to Winston | Custom middleware; Winston-only | Standard, minimal, integrates via a write stream | Extra dependency; justified by clean access-log separation. `npm audit --omit=dev` reports `morgan` `<1.12.1` as moderate: GHSA-jxfw-x594-9x9m (log forging via unescaped Unicode line separators) and GHSA-9f6g-j8ch-79g4 (log injection via an unescaped double quote in quoted fields such as referrer and user-agent). Partly mitigated: each access line is JSON-encoded inside a Winston entry, so `\n` and `"` are escaped and one request always yields exactly one parseable JSON line; inside the decoded `message`, a crafted user-agent or referrer can still spoof the quoted `combined` fields, and U+2028 passes through unescaped. Accepted risk: the `1.11.0` pin is retained per AAP §0.6.1 and the minimal-changes rule (the fixed `1.12.1` lies outside the pin, D28) |
| D4 | Add `helmet 8.2.0` + `compression 1.8.1` | Omit; add only if asked | "Prepare for production deployment" implies baseline security/perf middleware | Deviation from a literal reading of "middleware"; flagged under minimal-changes and justified as production hardening |
| D5 | `dotenv 17.4.2` for env config | convict; node-config; env-only | De-facto minimal standard; wrapped by one config module | `.env` could leak secrets; mitigated by `.gitignore` + committed `.env.example` |

None is in the runtime dependency tree (`npm audit --omit=dev` excludes them); they run in the PM2 CLI/daemon, not in the application workers, and pm2 uses `js-yaml` only to parse YAML ecosystem files, while this project ships a JavaScript one. Accepted risk: the `pm2` `7.0.3` pin is retained per AAP §0.6.1 and the minimal-changes rule (the fixed `7.0.4` lies outside the pin, D28) |

| D13 | Leave `server - Copy.js` untouched | Delete it; update it too | Minimal-changes rule; unreferenced duplicate outside the run path [server - Copy.js:L1-L14] | Duplicate remains; acceptable, out of scope |
| D14 | Sanitize centralized error handling: `errorHandler.js` returns the HTTP reason phrase for 4xx and a generic `Internal Server Error` for 5xx (never raw `err.message`), redacts query strings from every logged field (URL, detail, and the 5xx-only stack), and `notFound.js` builds its message from `req.path` (not `req.originalUrl`) so query strings are dropped at the source | (a) Keep returning/logging raw `err.message` (original impl); (b) gate exposure on the `err.expose` flag | Code review flagged a MAJOR security defect: raw messages leaked malformed-JSON parser internals to clients and echoed request query strings (e.g. `?token=secret`) into both responses and logs. Body-parser 400 errors carry `expose=true`, so `err.expose` alone would still leak parser detail; deterministic reason phrases are leak-free while preserving the AAP `{ error }` + `err.status \|\| 500` contract (D19 later restricts `err.status` to integers 400–599, which leaves every real error status unchanged) and the mandatory 4-argument error-handler arity. Morgan access logging (`combined` format, D22, in `app.js`) is unchanged and out of scope for this finding | Clients receive less-specific messages; mitigated by logging redacted diagnostics (status, method, query-redacted URL, detail, and stack for 5xx) server-side for debugging |
| D15 | Redact query strings from Morgan HTTP access logs: override Morgan's built-in `:url` token so it emits only the request path (the substring before `?`), keeping the `combined` format (D22) and the Winston `logger.stream` sink | (a) Keep plain `combined` (leaks the full query string); (b) redact only known-sensitive parameter names such as token/password via a custom token; (c) switch to a lighter `dev`/`short` preset | Code review flagged a MAJOR sensitive-data-in-logs defect (CWE-532): the `combined` `:url` token logged full URLs, so a request to `/unknown?token=secret` wrote `?token=secret` into the access log. Stripping everything from `?` onward guarantees no query value (known or unknown) is ever logged, extends to access logs the same query-redaction discipline already applied to error logs in D14, and preserves the combined format, the access-logging requirement, and the Morgan-to-Winston pipeline. Name-based redaction was rejected because it cannot enumerate every sensitive parameter and would still leak unknown ones | Access logs no longer include query strings, marginally reducing debugging signal; mitigated because method, path, status, size, referrer, and user-agent are all retained. Overriding a built-in token is module-global, but Morgan is instantiated exactly once so no other format is affected |
| D16 | Load dotenv via `require('dotenv').config({ quiet: true })` to suppress its startup console banner | (a) Leave the default banner (the `injected env ...` tip line); (b) set `DOTENV_CONFIG_QUIET=true` through the environment; (c) intercept and redirect stdout | dotenv 17.x prints an unstructured banner/tip to stdout on load, before Winston initializes, which breaks the structured-logging guarantee that all process output is Winston JSON. The pinned dotenv 17.4.2 supports the `quiet` option, so `{ quiet: true }` is the minimal, in-code, deterministic suppression that keeps startup output consistently structured | The informational injected-env line is hidden; mitigated because it carried no operational value, dotenv debug mode can be re-enabled ad hoc if needed, and Winston remains the single structured log source |
| D17 | For **4xx client errors**, log the deterministic HTTP reason phrase (plus the safe, enumerated body-parser `err.type`, e.g. `entity.parse.failed` / `entity.too.large`) as the server-side `detail`, instead of the raw `err.message`; **5xx** errors continue to log the query-redacted `err.message` and stack. This refines the server-side `detail` field described in D14's mitigation | (a) Keep logging `redactQuery(err.message)` for every status (the original D14 behavior); (b) redact only known secret patterns (token/password) from `err.message`; (c) drop the `detail` field entirely | Final acceptance flagged a MAJOR sensitive-data-in-logs defect (CWE-532): body-parser JSON syntax errors set `err.message` to a string that embeds a snippet of the raw request body (e.g. `Unexpected token 'P', "PASSWORD=s"... is not valid JSON`), and `redactQuery` strips only query strings, so that body snippet — potentially a secret — was written to the structured error log even though the client response was already sanitized. For a 4xx the message is derived from client-supplied input and adds no diagnostic value beyond the status and `err.type`, so the reason phrase plus `err.type` are sufficient and leak-free; 5xx messages are server-authored and retained (query-redacted) for debugging. Pattern-based redaction was rejected because it cannot enumerate every secret shape | 4xx error logs no longer include the parser's specific message; mitigated because status, method, query-redacted URL, and the enumerated `err.type` are retained, and the sanitized client `{ error }` response, the `err.status`-driven code, and the mandatory 4-argument arity are all unchanged |
| D18 | Harden the `server.js` lifecycle: (1) a server `'error'` listener writes one structured `logger.error` entry with the fixed text `HTTP server error` and the error's `code`, `syscall`, `address`, `port`, and `message` (Winston appends that `message` to the fixed text), then exits with code 1; (2) only the first SIGTERM/SIGINT starts shutdown, and later signals log one `warn` line each and never call `server.close` again; (3) an error passed to the `server.close` callback is logged at error level with its `code` and message and exits 1, otherwise `HTTP server closed` is logged and the process exits 0 as before; (4) shutdown starts a hardcoded `SHUTDOWN_TIMEOUT_MS = 4000` timer, `unref()`'d, that logs an error-level `Graceful shutdown timed out after 4000 ms: forcing exit` entry and exits 1 if connections have not drained | (a) Let Node crash on listen errors with its raw `Unhandled 'error' event` stack; (b) rely solely on PM2's SIGKILL after `kill_timeout` to end a hung shutdown; (c) make the timeout configurable through an environment variable; (d) call `server.closeAllConnections()` on timeout and let the close callback exit | A listen failure such as `EADDRINUSE` bypassed Winston and printed an unstructured stack on stderr, breaking the guarantee that all process output is structured Winston JSON. Repeated signals re-invoked `server.close`, the close callback discarded its error, and one held-open connection kept the process alive indefinitely after SIGTERM. Exit code 1 makes listen and shutdown failures visible to PM2 and operators. 4000 ms sits below PM2 `kill_timeout: 5000`, so a PM2 worker exits on its own with a logged reason before PM2 escalates to SIGKILL; a direct `node server.js` run has no SIGKILL backstop at all, which rules out (b). (c) was rejected because the refinement adds no environment variables. (d) was rejected because it reports a forced shutdown as a clean exit 0 and still depends on the close callback firing, whereas a timed exit is deterministic. `unref()` keeps the timer from holding the event loop open on its own | Requests running longer than 4 s are cut off during shutdown; a forced or failed shutdown returns exit code 1, which callers see as a failure even though the stop was requested. Mitigated because the clean path (`<SIGNAL> received: closing HTTP server` → `HTTP server closed` → exit 0) is unchanged and every forced or failed exit is logged at error level first. The timeout is a code constant, so changing it requires a code change |
| D19 | Normalize the error-response status and handle already-sent headers in `errorHandler.js`: the status is `err.status` only when it is an integer from 400 to 599, otherwise 500, and the client message, the logged `detail`, `type`, and the 5xx-only `stack` all derive from that normalized status (`err.statusCode` is not consulted); when `res.headersSent` is true the handler still writes the same sanitized Winston error entry, then destroys the connection with `req.socket.destroy()` and returns without calling `res.status().json()` or `next(err)`, keeping the 4-argument arity | (a) Keep `err.status \|\| 500`; (b) accept any `typeof err.status === 'number'` in 400–599 without an integer check; (c) also honour `err.statusCode`; (d) follow the Express-documented `if (res.headersSent) return next(err)` delegation; (e) finish the partial response with `res.end()` | Refinement review reproduced two defects: an error with `err.status` 200 returned HTTP 200 `{"error":"OK"}` and one with 600 returned HTTP 600, and an error raised after a handler had already written part of the body made `res.status().json()` throw `ERR_HTTP_HEADERS_SENT` inside the error handler. Restricting the range to 400–599 matches Express's own default handler and leaves every real error status and the missing-status default exactly as `err.status \|\| 500` produced them (the 404, 400 `entity.parse.failed`, and 413 `entity.too.large` responses are unchanged). The integer check goes beyond a plain `typeof` test because Express 5 `res.status()` throws on any non-integer code (verified with `400.5`, and with the string `'404'` before this change), and that throw escaped to the default handler, which answered with an HTML page containing the raw stack. `err.statusCode` is not honoured so that `err.status` stays the single source of the code. Delegating to `next(err)` was rejected because Express's default handler prints the raw, unredacted `err.stack` through `console.error`, bypassing the D14/D17 redaction and the all-Winston-JSON output; `res.end()` was rejected because a truncated body would look complete to the client, whereas destroying the socket, as Express's finalhandler does, makes the client observe an incomplete response | A library error carrying only `statusCode` (no `status`) now maps to 500; mitigated because Express's body parsers and `http-errors` set both properties, so the built-in 4xx errors are unaffected. A partially streamed response is cut off and its keep-alive connection closed, and the logged `status` reflects the error rather than the status line already sent; mitigated because the client sees a reset or incomplete message instead of a seemingly valid body, and the sanitized Winston entry records the failure |
| D20 | Route **error-level** Winston output to stderr: the single Console transport in `src/config/logger.js` is constructed with `stderrLevels: ['error']`. Every other level (`warn`, `info`, and the Morgan access lines that `logger.stream` writes at `info`) stays on stdout. The timestamp + JSON line format, the logger level, and the `logger.stream` adapter are unchanged | (a) Keep every level on stdout (the Console transport default, the original behavior); (b) `stderrLevels: ['error', 'warn']`; (c) add a Winston File transport for errors | PM2 writes a process's stdout to `out_file` (`./logs/out.log`) and its stderr to `error_file` (`./logs/error.log`). With every level on stdout, the 404/400 error entries appeared on stdout while stderr stayed empty, so `./logs/error.log` never received application errors. Sending `error` to stderr realises the PM2 log routing already configured in `ecosystem.config.js` through an option of the existing Console transport, with no new transport, file handle, or dependency. `warn` stays on stdout because no code path emits it, so widening the set would change behavior without a defect to fix. A File transport was rejected because it duplicates the file persistence PM2 already provides and adds a second write path per cluster worker | Consumers that read only stdout (for example `node server.js > app.log`) no longer see error lines; mitigated by redirecting both streams (`2>&1`) for direct runs, while PM2 captures both into its two files. `warn` entries, if ever emitted, go to `./logs/out.log` rather than `./logs/error.log`. Under PM2 error and access lines live in separate files, so correlating them relies on each line's `timestamp` |
| D21 | Register `express.urlencoded({ extended: false })` in `src/app.js` (next to `express.json()`): form bodies are parsed flat. The pinned body-parser `2.3.0` calls `qs.parse` with `depth: 0`, so `a[b]=1&c=2&c=3` yields `{"a[b]":"1","c":["2","3"]}` (bracket keys stay literal, repeated keys become arrays) | (a) `extended: true` (`qs` nested objects, default `depth: 32`: the same body yields `{"a":{"b":"1"},"c":["2","3"]}`); (b) register only `express.json()` and omit form parsing; (c) a standalone `body-parser` dependency | AAP §0.1.1 and §0.4.2 name `express.urlencoded()` as part of the body-parsing middleware. No route reads form fields, so flat parsing is the smallest parsing surface: no nested-object construction or bracket-key expansion. `extended: false` matches classic `querystring` semantics and the body-parser 2.x default, stated explicitly so the intent is visible. Express 5 provides the parser natively, so no extra dependency is needed | Clients posting nested form fields (`user[name]=x`) receive flat literal keys, not objects; no current route consumes `req.body`, so there is no functional impact, and a future form route can opt into `extended: true` with an explicit `depth`. Bodies over body-parser's default `parameterLimit` of 1000 fields are rejected with `413`. `qs` remains a transitive dependency (advisories recorded under D1) |
| D22 | Log HTTP requests in Morgan's predefined `combined` format (Apache combined log: remote address, remote user, date, method, URL, HTTP version, status, content length, referrer, user-agent) via `morgan('combined', { stream: logger.stream })` in `src/app.js` | `dev` (coloured, terse terminal output); `common` (no referrer/user-agent); `short`/`tiny` (minimal fields); a custom format built from JSON tokens so each field becomes a separate Winston property | The AAP mandates Morgan piped into Winston (§0.2.2, §0.4.2) but names no format; this choice is the implementation's. `combined` is the de-facto production access-log standard, carries the referrer and user-agent needed for troubleshooting, is understood by standard log analysers, and needs no custom token code. `dev` emits ANSI colour codes that do not belong inside JSON entries, and `common`/`short`/`tiny` drop diagnostic fields | Each access line is one string in the Winston `message` field rather than discrete JSON fields, so filtering by status or method requires parsing the string. The built-in `:url` token logged query strings (fixed by D15). Referrer and user-agent are client-controlled and are the vector of the `morgan` advisories recorded under D3. `:remote-addr` is the socket address because `trust proxy` is not set, so behind a reverse proxy every request logs the proxy's address until `trust proxy` is configured for that deployment |
| D23 | Configure Winston (`src/config/logger.js`) with `format.combine(timestamp(), json())` and a single `transports.Console`; persistence to disk is delegated to PM2 (`out_file: './logs/out.log'` for stdout, `error_file: './logs/error.log'` for stderr in `ecosystem.config.js`); no log rotation is configured | (a) `winston.transports.File` per level; (b) `winston-daily-rotate-file` (`DailyRotateFile`) transport; (c) the `pm2-logrotate` module; (d) human-readable `simple()`, `printf` or `prettyPrint()` formats; (e) a separate logger/transport for access logs | One JSON object per line with an ISO-8601 `timestamp` is machine-parseable and satisfies "structured logging" (AAP §0.4.2 specifies a console transport with timestamp/JSON format). Writing only to the process's standard streams follows the 12-factor log-stream convention, lets PM2 collect every cluster worker's output into one file pair (`merge_logs: true`, D25), and avoids several workers appending to the same file through in-process File transports. Rotation was not requested, and every rotation option adds a dependency or a PM2 module, which the minimal-changes rule excludes | Without rotation `./logs/out.log` and `./logs/error.log` grow without bound; mitigated operationally (host `logrotate` or `pm2 install pm2-logrotate`) with no code change. Under plain `node server.js` nothing is persisted unless the operator redirects the output. PM2 prefixes each persisted line with its `log_date_format` timestamp (`<date>: <JSON>`), so file lines carry two timestamps and must have the prefix stripped before JSON parsing |
| D24 | The Morgan stream adapter `logger.stream.write` calls `logger.info(message.trim())`: access lines are logged at Winston level `info`, with the trailing newline Morgan appends removed | (a) Winston's `http` level (npm level 3, one below `info`); (b) a dedicated access logger or transport; (c) pass the message untrimmed | Winston's npm levels are `error` 0, `warn` 1, `info` 2, `http` 3, so the default `LOG_LEVEL=info` (from `src/config/index.js`, `.env.example`, and both PM2 env blocks) suppresses `http`; access logs written at `http` would silently disappear in every shipped configuration. `info` keeps them visible with no extra setting. Trimming stops every JSON `message` from ending in an escaped `\n` | Access logs cannot be silenced or raised independently of application `info` logs: `LOG_LEVEL=warn` hides both. | D25 | PM2 tuning values in `ecosystem.config.js`: `instances: 'max'`, `max_memory_restart: '300M'`, `max_restarts: 10`, `min_uptime: '10s'`, `kill_timeout: 5000`, `autorestart: true`, `watch: false`, `merge_logs: true`, `log_date_format: 'YYYY-MM-DD HH:mm:ss Z'`, and the relative paths `./logs/out.log` / `./logs/error.log` | A fixed worker count (e.g. `instances: 2`) or `-1` (all cores but one); no memory ceiling, or a different one; the PM2 defaults (`max_restarts` 16, `min_uptime` 1000 ms, `kill_timeout` 1600 ms, `merge_logs` false); `watch: true`; per-worker log files; absolute log paths (e.g. under `/var/log/`) or PM2's default `~/.pm2/logs/` | `'max'` runs one worker per CPU (D6). 300 MB is a generous ceiling for a stateless Hello-World service and recycles a leaking worker before it starves the host. `max_restarts: 10` with `min_uptime: '10s'` stops a crash-looping app instead of restarting it forever: a worker that exits within 10 s counts as an unstable restart. `kill_timeout: 5000` gives the SIGTERM/SIGINT handler in `server.js` 5 s to drain connections before SIGKILL, instead of PM2's 1.6 s default; the handler's own 4000 ms forced exit (D18) ends a stalled drain before PM2 escalates. `autorestart: true` revives crashed workers. `watch: false` because file watching is a development feature that would restart production on any file change. `merge_logs: true` writes all workers to one file pair instead of per-worker files suffixed `-<pm_id>.log`. `log_date_format` adds a timezone-qualified, PM2-side timestamp. Relative `./logs/` keeps logs inside the project (git-ignored as `logs/`), and PM2 creates the folder on start, so there is no root-owned directory to provision | `'max'` follows the CPU count PM2 detects (24 on the build host), which can over-commit memory on shared hosts; override `instances` per host. 300M may recycle workers under real load; tune it from monitoring. After 10 unstable restarts the app stays `errored` until restarted manually. Relative paths resolve against the directory PM2 is launched from: `npm run pm2:*` runs from the package root, but `pm2 start` invoked from another directory resolves `server.js` and both log files against that directory. Double timestamps in persisted lines (D23) |
| D26 | The `env` and `env_production` blocks of `ecosystem.config.js` hardcode `NODE_ENV`, `PORT`, `HOST` and `LOG_LEVEL` (`env`: `development`, `3000`, `127.0.0.1`, `info`; `env_production`: `production`, `3000`, `0.0.0.0`, `info`).
